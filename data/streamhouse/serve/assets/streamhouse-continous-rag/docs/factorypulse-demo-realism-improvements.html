🔴 High Impact — Demo breaks without these

These directly affect whether an audience understands the Continuous RAG freshness story.

1. Demo knowledge is too thin and too generic

HIGH

All four demo_knowledge/ files are 4–7 short sentences. Real work orders, SOPs, and OEM guides are 400–1 500 words with specific part numbers, torque specs, inspection intervals, and failure signatures. With thin content, the hash-embedding retrieval has almost nothing to differentiate — all scores cluster near 0.4.

  • Fix: Expand each file to 400–600 words with realistic manufacturing detail: part numbers, tolerance windows, step-by-step procedures, named technicians, timestamps, shift numbers.
  • Add 3–4 more documents: a quality alert, a shift handover log, a tooling calibration record, and a preventive maintenance schedule.
  • Why it matters: Richer content produces wider score spread, makes evidence cards meaningful, and gives the audience something to read that feels real.
demo_knowledge/app/main.py seed-knowledge

2. WO-11023 resolution text is too vague for RAG freshness proof

HIGH

The "Resolve + Learn" step streams a work order with only 3 sentences. After indexing it ranks at score 0.2402 — below some baseline docs on certain questions. The audience sees it at top-1 on the specific "WO-11023" query but not on broader operational questions.

  • Fix: Expand the resolution note in _build_demo_step("resolved") to include: torque spec (45 Nm), bearing part number, inspection photos noted, technician ID, shift number, recommended inspection interval (200 hrs), and a before/after vibration table.
  • Why it matters: Richer resolution text makes it the clear top hit on any CNC-03 question asked after the resolve step — which is the core freshness proof.
app/main.py:332resolved step

3. Hash embedding cannot distinguish semantically similar documents

HIGH

The HashEmbeddingModel uses token-frequency hashing — not semantic similarity. Two documents about "spindle bearing replacement" and "tool-holder imbalance" will have very similar hashes because they share many tokens. This is the real reason all evidence scores are bunched between 0.12–0.41.

  • Short fix: Add a per-question keyword boost — after cosine retrieval, re-rank evidence that contains exact tokens from the question higher. This is cheap and makes retrieval visibly smarter without changing the embedding model.
  • Real fix: Upgrade to STANDARD cluster + Confluent Flink AI_EMBEDDING. Everything is already written — infra/flink/continuous_rag.sql is ready. This is the strongest demo of the Streamhouse value.
app/services/embedding.pyapp/services/vector_index.py

4. LLM_PROVIDER=none produces extractive answers that break immersion

HIGH

Every RAG answer ends with "This response is intentionally extractive because LLM_PROVIDER=none. Configure watsonx.ai…" — this is a meta-comment that pulls the audience out of the manufacturing story. Even without watsonx, the answer can be more professional.

  • Fix: Replace the DeterministicGroundedGenerator answer template with a structured format: a one-sentence direct answer derived from the top evidence title/text, a numbered "Evidence used" list citing each chunk, and a footer line showing freshness timestamp. Remove the "configure watsonx.ai" sentence — it belongs in the Settings tab, not every answer.
app/services/llm.py:23

5. Demo scenario steps are invisible on the Streamhouse / Live Events tab

HIGH

When you click Baseline → Degrade → Critical, the Overview updates but the Live Events feed stays empty (populated only from store.events which is never written by the demo step handler). The audience cannot see the Kafka events flowing — which is the whole point of the Streamhouse story.

  • Fix: In _on_factory_state, _on_exception, and _on_document callbacks, push a typed event object into store.events. Show type, a 1-line summary, and timestamp in the Live Events feed.
  • Also: The SSE stream should include recent events in its snapshot payload so the feed populates on first load.

7. No progressive scenario — audience must click 4 buttons manually

MEDIUM

A polished demo auto-advances through baseline → degrade → critical on a timer when the presenter clicks "Start demo". The current 4-button approach is fine for a technical walk-through but weak for a live presentation where the presenter is talking and cannot multitask.

  • Fix: Add a "Start demo (auto)" button that runs baseline → (15 s) → degrade → (20 s) → critical, with a countdown visible in the toolbar. Each transition shows a toast. The presenter just talks.

8. Evidence cards truncate at 330 chars — key facts are cut off

MEDIUM

The evidence card renderer cuts text at 330 characters with "…". For the hash embedding model this is fine, but once real content or watsonx is added, the most important sentence (often the conclusion/recommendation) is frequently in the second half of the chunk.

  • Fix: Increase truncation to 500 chars, or add a "Show more" inline expand toggle per card. Also display the updated_at as a relative time ("2 minutes ago") to make freshness visceral.
app/static/app.js:85

9. Kafka probe latency of 2031 ms makes the chip feel slow

MEDIUM

The AdminClient.list_topics() probe takes ~2 s because it creates a new AdminClient on every call. The result is cached 10 s but the first call on page load makes the chip show "Checking…" for 2 seconds before showing "Connected".

  • Fix: Run the probe once at app startup (in lifespan) to warm the cache, so the first page load shows the connected state immediately. The 10 s cache keeps subsequent calls fast.

🟣 Architecture Upgrade — Strongest Confluent story

13. Upgrade to STANDARD cluster for real Flink AI embeddings

ARCH

The single biggest realism improvement is switching from the hash embedding demo to real semantic embeddings via Confluent Cloud Flink AI_EMBEDDING. This eliminates the score-clustering problem, produces genuinely semantic retrieval, and lets you say "the same Kafka + Flink platform doing your operational joins is also doing your AI embeddings — one system".

  • Already prepared: infra/flink/continuous_rag.sql is complete. infra/confluent/terraform/main.tf has STANDARD cluster support. infra/confluent/flink/tables.sql has the Flink-owned DDL.
  • Steps: Set cluster_type = "STANDARD" in terraform.tfvars → terraform apply → run the Flink SQL → set RAG_PIPELINE_MODE=flink + SERIALIZATION_MODE=schema-registry-json.
  • Cost: STANDARD cluster + Flink CFUs. Turn off the Flink compute pool after the demo to avoid ongoing cost.

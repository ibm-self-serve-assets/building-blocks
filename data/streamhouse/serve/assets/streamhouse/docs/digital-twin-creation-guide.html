Section 1

What is a digital twin?

A digital twin is a continuously updated software model of a physical object or system. Factory Pulse models a network of six fictional US manufacturing plants, each with robots, conveyors, and automated guided vehicles (AGVs).

The twin is built from three interdependent layers:

1
Simulation
Generates synthetic but physically plausible sensor readings on every clock tick. Applies scenario-based fault injection to create realistic anomalies for demonstration.
Python · FactorySimulation · plants.py · simulation.py
2
Event stream
Transports every sensor reading as a structured event from the simulator to all consumers. Schema Registry enforces message contracts. Flink SQL derives secondary analytics streams.
Confluent Kafka · Schema Registry · Apache Flink SQL · Tableflow
3
Visualisation
Renders the live simulation state as an interactive 3D factory floor, real-time KPI dashboard, trend charts, event feed, and AI context panel — all driven by Server-Sent Events from the backend.
React · React Three Fiber · Three.js · Recharts · Carbon Design System

Section 3

Simulation engine

The FactorySimulation class in server/simulation.py is the engine. It initialises a state object for each site and advances it on every call to step().

Simulation tick

The Flask background thread calls sim.step() every 1 700 ms (configurable via SIM_INTERVAL_MS). Each tick:

  1. Increments the global tick counter.
  2. Loops over every site and every robot within that site.
  3. Applies sinusoidal noise to each sensor reading — the noise is offset by the site's seed integer to give each plant a distinct signal shape.
  4. Applies the active scenario multiplier to distort signals (see Section 5).
  5. Evaluates alert thresholds to derive the robot's status.
  6. Recomputes site-level OEE and throughput.
  7. Appends a rolling history entry (55-tick buffer) for trend charts.
  8. Selects 2 robots per site (round-robin) and emits factory-iot-telemetry records.
  9. Every 3 ticks, emits factory-asset-state for the first 3 robots per site.
  10. Every 5 ticks (if a fault is active at ≥ 35 % severity), emits a factory-maintenance-events alert.
  11. Broadcasts the full snapshot to all SSE listeners.

OEE formula

Overall Equipment Effectiveness is smoothed on each tick using an exponential moving average:

site_oee = site_oee × 0.67 + target_oee × 0.33

Throughput formula

throughput = lines × 16 × (oee / 98)   # ×1.25 during surge; 0 when paused

Sinusoidal noise

Each robot signal is computed as a base value plus a small sine-derived noise term, ensuring readings feel live without being chaotic:

noise = sin(tick × freq + seed × phase_offset) × amplitude

Section 7

Schema governance

When running in Kafka mode, the backend registers JSON Schema contracts in Confluent Schema Registry before producing any messages. Schemas are defined in server/schemas.py.

Subject naming convention

Follows TopicNameStrategy: each topic gets a -key and -value subject, e.g., factory-iot-telemetry-value.

Wire format

Each message is encoded with Confluent's binary wire format: a 1-byte magic byte (0x00) followed by a 4-byte schema ID, then the JSON payload. This allows every consumer to retrieve the correct schema version from the registry.

Schema strictness

All value schemas use "additionalProperties": false, ensuring downstream consumers (Flink, Tableflow, RTCE) reject malformed messages at the contract boundary.

Section 8

Stream processing — Flink SQL

Four SQL files in flink/ implement the TRANSFORM layer. They run on a Confluent Cloud Flink compute pool — not embedded locally.

FileWhat it does
01-create-tables.sqlDeclares the three derived output tables. Source tables are inferred from Schema Registry — no CREATE TABLE needed for them.
02-risk-signal.sqlPer-event INSERT INTO … SELECT that classifies each sensor reading into BEARING_RISK, THERMAL_RISK, or QUALITY_RISK using CASE WHEN threshold logic.
03-shift-kpis.sql1-minute tumbling window aggregates: sample count, mean temperature/vibration/quality, and kWh estimate per site.
04-quality-alerts.sqlFilters qualityScore < 86 and routes to REQUEST_INSPECTION (78–86) or QUARANTINE_BATCH (< 78).

Tumbling window

A Flink windowing pattern that groups events into fixed, non-overlapping time intervals. The shift KPIs SQL uses a 1-minute window on the $rowtime attribute, which Confluent Flink infers from the Kafka message timestamp.

Section 11

Robot arm kinematics

Each robot is a 6-axis articulated arm built from a hierarchy of THREE.Group nodes. Every joint group pivots around its local Y=0 origin, which is placed at the joint centre when the group is positioned.

Joint hierarchy

root (world position + rotOffset facing direction) └ base collar + accent rim (static geometry) └ j1 Y-axis — waist swivel └ waist cylinder (static geometry) └ j2brkt — shoulder bracket + ear plates + pivot bolt (static) └ j2 Z-axis — shoulder pitch └ upper arm geometry (3-section tapered cylinder) └ cable conduit (static on back of upper arm) └ j3brkt — elbow bracket + pivot bolt (static) └ j3 Z-axis — elbow bend └ forearm tube (tapered cylinder) └ j4 roll housing (collar with accent torus) └ j4 Y-axis — forearm roll └ wrist housing (cylinder) └ j5 Z-axis — wrist pitch └ wrist body (tapered cylinder) └ j6 tool flange (cylinder + accent torus) └ j6 Y-axis — tool spin └ end-effector geometry (role-specific tool)

Joint axis conventions

JointGroup refRotation axisMotion
j1j1YWaist swivel — azimuth sweep left/right
j2j2ZShoulder pitch — pitches arm forward/back; +Z = forward (toward belt)
j3j3ZElbow bend — curls forearm; −Z = folds under (brings tip down)
j4j4YForearm roll — rotates tool about the forearm's long axis
j5j5ZWrist pitch — fine angle adjustment of the tool
j6j6YTool spin — rotates the end-effector

REST pose — reaching the belt

The REST pose is the shared baseline from which all per-robot kinematic deltas are applied. It is tuned so the tool tip rests approximately at belt-surface height (world Y ≈ 0.63):

const REST = {
  j1y:  0,       // waist centred
  j2z:  1.10,    // shoulder pitched forward toward belt
  j3z: -1.45,    // elbow folded under, bringing forearm horizontal
  j4y:  0,       // forearm roll neutral
  j5z:  0.28,    // wrist levelled so tool face points toward belt surface
  j6y:  0,       // tool spin neutral
};
Why the REST pose matters Without a REST pose baseline the arms point upward (the Three.js default for Y-up geometry). The REST pose pre-pitches the shoulder 1.10 rad forward and curls the elbow −1.45 rad under so the arm geometry naturally drapes toward the belt. Each robot's kinematic function then adds small deltas on top of these values for its specific motion pattern.

Phase stagger

Each robot is offset by i / 6 of the 7-second cycle so the work wave rolls sequentially down the line:

const phase = ((now / CYCLE) + i / 6) % 1;   // i = robot index 0–5

Section 13

AI context & MCP

Rule-based demo context (context.py)

The POST /api/context endpoint uses regex keyword matching on the user's question and returns a deterministic, transparently labelled demo answer. It is explicitly not an LLM call.

Regex triggerResponse topic
maintenance|failure|risk|bearing|criticalMaintenance risk — lists robots above threshold
quality|reject|yieldQuality and yield — average quality score
energy|power|consumptionEnergy — total modelled kW load
(default)Live operations briefing — OEE, throughput, robot count

Confluent RTCE MCP connector (mcp.py)

A real integration with Confluent Real-Time Context Engine (RTCE) via the Model Context Protocol (MCP) over a streamable-HTTP transport. Activates only when RTCE_MCP_ENDPOINT and RTCE_MCP_BASIC_TOKEN are set.

Credentials never leave the server. The browser calls /api/mcp/tools and /api/mcp/call; the Flask route proxies to RTCE via an async anyio.run() session.

Analytical path — Tableflow + Apache Iceberg

Tableflow materialises governed Kafka topics as Apache Iceberg tables in object storage. IBM watsonx.data connects to the Iceberg catalog for governed SQL queries over the full telemetry history — no separate ETL pipeline required.

Operational path — RTCE + MCP + watsonx Orchestrate

RTCE materialises the latest value of each factory-asset-state record as a low-latency context store. IBM watsonx Orchestrate calls RTCE MCP tools to read current robot state and act autonomously — for example, scheduling maintenance when health drops below threshold.

Section 15

Glossary of all terms

AGV (Automated Guided Vehicle)
Wheeled robot that transports parts along the factory floor. Modelled in Three.js as a yellow box cart oscillating along X.
Alert
Structured event emitted when a sensor reading crosses a threshold. Severity is warning or critical.
Apache Flink
Distributed stream-processing framework. Factory Pulse uses Confluent Cloud for Apache Flink to run SQL queries continuously over Kafka topics.
Apache Iceberg
Open table format for large analytical datasets. Used in the analytical path to provide SQL-queryable history from Kafka via Tableflow.
Asset ID
Unique identifier for a robot, e.g., DET-R01. Composed of the site ID and a zero-padded role index.
batchId
Production batch identifier in the telemetry record. Increments every 12 simulation ticks.
Bearing wear
A fault scenario that increases vibration to simulate progressive mechanical degradation of a spindle bearing.
Canvas (R3F)
React Three Fiber's root component. Creates a WebGL context; JSX children like <mesh> map to Three.js objects.
Cobot
Collaborative robot. The Assembly cobot (R4) works alongside humans on the production line performing fastener driving.
Compute pool
Managed Flink resource in Confluent Cloud on which SQL statements run. Must be provisioned before deploying the Flink SQL files.
ContactShadows
A @react-three/drei utility that adds soft drop shadows beneath objects without per-mesh shadow receivers.
Conveyor belt
Single centre-line belt carrying parts (world Z = 0). Parts travel right → left at 1.3 world-units / second; belt surface at world Y = 0.54, parts at Y = 0.63.
Digital twin
A continuously updated software model of a physical system. In Factory Pulse, each factory site has a digital twin maintained by the simulation loop.
Derived topic
A Kafka topic whose data is produced by a Flink SQL transformation rather than directly by the simulator, e.g., factory-risk-signals.
energyKw
Instantaneous electrical power draw of a robot in kilowatts. Increases during thermal excursion and surge scenarios.
EventSource
Browser Web API used to receive Server-Sent Events from /api/events over a persistent HTTP connection.
Fault injection
Deliberate introduction of an anomaly (bearing, thermal, quality, or surge) via the UI to demonstrate the detection and response pipeline.
Flink Topic Action
A Confluent Data Portal feature that applies built-in Flink transformations (deduplicate, mask, transform) to a topic without writing SQL.
health
Composite integer score 0–100 representing the overall condition of a robot asset. Degrades under fault scenarios; reset to 99 by maintenance action.
history
Rolling 55-tick buffer of { t, output, oee, temp, vibration, quality } per site, used to render the MiniTrends area charts.
Intensity / severity
Scale factor 0–100 % applied to a fault scenario's signal distortion. Higher intensity = larger deviations and faster OEE degradation.
j1 – j6
The six joint groups in each robot arm. j1 = waist (Y), j2 = shoulder pitch (Z), j3 = elbow bend (Z), j4 = forearm roll (Y), j5 = wrist pitch (Z), j6 = tool spin (Y).
JSON Schema
A vocabulary for annotating and validating JSON documents. Used as the contract format for all Kafka topics in this demo.
kinematic function
A per-robot JavaScript function that receives elapsed time t and cycle phase ph (0–1) and returns the six joint angle deltas on top of the REST pose.
lineId
Identifies which production line a robot belongs to within a site. Values cycle as LINE-1, LINE-2, LINE-3.
MCP (Model Context Protocol)
Open protocol for connecting AI agents to live data tools. Confluent RTCE exposes factory context via MCP; the backend proxies calls via mcp.py.
MES (Manufacturing Execution System)
Category of plant software (alongside SCADA and ERP) that Factory Pulse is conceptually augmenting, not replacing.
mock mode
Default operational mode when STREAM_MODE is not kafka. Events are queued in memory; no Confluent Cloud credentials required.
OEE (Overall Equipment Effectiveness)
Manufacturing KPI (target ≥ 95 %) combining availability, performance, and quality. Computed here as a smoothed exponential moving average.
OrbitControls
A drei / Three.js control that lets users drag to orbit and scroll to zoom the 3D factory view.
phase
A 0–1 progress value within the robot's 7-second animation cycle, used as the input to kinematic functions.
qualityScore
Simulated first-pass yield percentage for a robot. Drops significantly during a quality drift scenario.
React Three Fiber (R3F)
A React renderer for Three.js. <Canvas> creates a WebGL context; components like <mesh> map to Three.js objects.
Recharts
React charting library used for the area trend charts in the twin overview panels.
REST pose
The shared baseline joint angles all 6 robot arms start from before per-robot kinematic deltas are applied. Tuned so the tool tip rests at belt-surface height.
rotOffset
The initial rotation.y applied to a robot's root group. Front-row robots = 0 (face toward belt); back-row = π (face toward belt from other side).
rpm
Revolutions per minute. Simulated motor speed of a robot's drive shaft. Increases during surge scenario.
RTCE (Real-Time Context Engine)
Confluent feature that materialises the latest Kafka record per key as a queryable, low-latency context store, exposed via MCP.
SASL_SSL
Security protocol for the Confluent Kafka producer: SASL (Simple Authentication and Security Layer) over TLS/SSL.
scenario
One of five operation modes: baseline, bearing, thermal, quality, surge. Each modifies sensor physics during the simulation step.
Schema Registry
Confluent central repository for JSON Schema / Avro / Protobuf contracts. Factory Pulse registers JSON Schema subjects before producing any messages.
seed
Per-site integer 0–5 used as a phase offset in sinusoidal noise functions to differentiate each plant's signal pattern.
siteId
Two or three-character plant code: DET, AUS, SEA, PHX, CLT, CHI.
snapshot
The full serialised state of the simulation at a given tick, broadcast to all SSE clients on every step.
SSE (Server-Sent Events)
Unidirectional HTTP streaming protocol used to push live factory state from the Flask backend to the browser.
status
Per-robot: running (nominal), warning (threshold exceeded), stopped (site paused). Per-site: healthy, warning, idle.
Streamhouse
IBM and Confluent's reference architecture for streaming data integration, comprising Kafka, Flink, Stream Governance, Tableflow, and RTCE.
Tableflow
Confluent Cloud feature that materialises Kafka topic records as Apache Iceberg tables stored in object storage.
temperature
Simulated surface/motor temperature in °C. Rises sharply during a thermal excursion scenario.
Three.js
JavaScript 3D rendering library. React Three Fiber wraps it for use inside React components.
throughput
Number of units produced per minute by a factory site, derived from OEE and line count.
tick
A single simulation step. Increments on every sim.step() call, which fires every 1 700 ms by default.
Tumbling window
Flink windowing pattern that groups events into fixed non-overlapping intervals. Used in the shift KPIs SQL with a 1-minute interval.
useFrame
React Three Fiber hook that registers a callback executed on every animation frame. Used for robot kinematics and conveyor animation.
vibration
Simulated bearing/spindle vibration in mm/s. The primary diagnostic signal for bearing wear detection.
watsonx.data
IBM open lakehouse data platform. Connects to Iceberg tables produced by Tableflow for governed historical analytics.
watsonx Orchestrate
IBM AI agent orchestration platform. Downstream consumer of RTCE MCP tools for automated factory operations.
Webhook
Optional HTTPS POST called by the backend when a maintenance action is triggered; dispatches the event to an external service desk.
Wire format
Binary Confluent encoding prepended to each Kafka message: 1 magic byte (0x00) + 4-byte schema ID + JSON payload.
world coordinates
The Three.js scene uses Y-up coordinates. Belt surface = Y 0.54, parts = Y 0.63, robot bases = Y 0. Front-row robots at Z = −3.5, back-row at Z = +3.5.
